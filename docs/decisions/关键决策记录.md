## ADR-008 · tshark 输出改用 -e 精选字段,JSON 上限提至 128MB(2026-08-25)

- **状态**:✅ 已定(2026-08-25,现网 20MB+ 抓包打开失败驱动)
- **背景**:`-T json -J "frame eth …"` 全协议树模式实测每包膨胀 5-6.5KB(44 倍),20MB 抓包 ≈ 110-160MB JSON,撞 64MB 上限报 "capture too large";现网抓包普遍超过该档位。
- **决策**:
  1. **输出瘦身优先于抬上限**:tshark 改用 `-T json -e <字段>` 平铺模式,只取 pUI 用到的 33 个字段(清单 `tshark::CAPTURE_FIELDS`),实测输出缩小 4-5 倍(lossy 26.8KB→5.5KB,http 58KB→11.9KB);
  2. JSON 上限 64MB → **128MB**(前端 `MAX_PARSE_JSON` 同档),等效可开约 90-100MB 抓包(8-10 万包);
  3. 解析器双形态兼容:平铺键优先,协议树回落(旧产物/旧 fixture 不破坏);`dns.flags.response` 的 `-e` 取值(True/False)与树取值(1/0)都识别;
  4. 超限错误信息改为可操作指引(显示过滤 / editcap 分割)。
- **后果**:20MB 级现网抓包可正常打开;字段清单是前后端契约(新增前端字段须同步 `CAPTURE_FIELDS` 与 `scripts/gen-parsed.mjs`);GB 级抓包仍需 v1.1 流式/分段解析(`-T ek` NDJSON),128MB IPC 传输仍有数秒级开销。

## ADR-007 · 安全加固:能力面收窄 + 资源上限(2026-08-08)

- **状态**:✅ 已定(2026-08-08,安全审查驱动)
- **背景**:三方审查(业务逻辑 / 安全 / 前端健壮性)定位出一批加固点;本 ADR 记录其中的架构/能力面类第三档决策。
- **决策**:
  1. **tshark 路径能力模型**:`set_tshark_path` 仅接受「绝对路径 + 文件存在 + 文件名含 tshark」,收窄「set_tshark_path + open_capture = 任意二进制执行」的能力面;已知信任模型为「自定义解析器路径即授予该进程执行权」,前端为自有可信代码,不加载远程内容。
  2. **大抓包内存**:tshark `-T json` 输出改为流式读取并设 **128MB** 上限(超过即终止子进程),输入文件 **512MB** 直接拒绝;渲染层 `JSON.parse` 仍在主线程,超大文件留待 v1.1 流式/分段解析。
  3. **CSP**:生产 `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ipc: http://ipc.localhost`;开发用 `devCsp` 额外放行 HMR(`ws://localhost:*` 与内联脚本)。
- **后果**:直接可触达的 DoS(超大 pcap OOM)被上限挡住;能力面显著收窄;渲染层当前无 XSS sink 时 CSP 提供纵深防御。

## ADR-006 · 内置示例抓包(F7)

- **状态**:✅ 已定(2026-08-07)
- **背景**:使用场景含「教学 / 演示」,开箱即用体验需要示例。
- **决策**:v1.0 随包附带 2–3 个示例抓包(HTTP、DNS、ARP/TCP 混合),提供「打开示例」入口。
- **后果**:演示零门槛;示例同时用作集成测试 fixtures,一物两用。

## ADR-005 · 时序图双风格 A/B + 方向色(PRD §6 F4)

- **状态**:✅ 已定(2026-08-07,经可视化对比确认)
- **背景**:用户参考原型为 flow.png 斜线交叉风格;但报文多时交叉密集,可读性下降。
- **决策**:默认风格 A(flow.png 斜线交叉)+ 风格 B(水平消息行),一键切换;线色=协议色,方向用步骤徽章/箭头(请求蓝 ● / 响应橙 ●),可选整线按方向着色。
- **后果**:满足参考原型又保证可读性;渲染层按「同一数据源 + 两套布局函数」实现,切换零成本。

## ADR-004 · 三栏常驻布局(PRD §7)

- **状态**:✅ 已定(2026-08-07,经可视化对比确认)
- **背景**:三大核心内容(筛选 / 会话列表 / 时序图)需同屏协同。
- **决策**:三栏常驻(左筛选 | 中会话列表 | 右时序图)+ 顶部工具条。
- **后果**:筛选项始终可见、改筛选即时生效;窄屏下右图空间受限(可接受)。

## ADR-003 · 筛选语义 = 会话级(PRD §6 F2)

- **状态**:✅ 已定(2026-08-07)
- **背景**:「筛协议=X」到底画什么有歧义;几十万报文直接画图必爆炸。
- **决策**:两级粒度——筛选收敛「会话列表」,点进会话再看「报文时序图」;会话内任一报文命中即命中会话。
- **后果**:避免图爆炸,交互路径清晰;会话内报文过滤留作 v1.1。

## ADR-002 · 时序图渲染用自绘 SVG(PRD §9)

- **状态**:✅ 已定(2026-08-07)
- **背景**:需精确实现编号/时间/长度/方向色/协议色/悬停/点击详情/双风格。
- **决策**:React 自绘 SVG,不引入 Mermaid/G6/React Flow 等图库。
- **后果**:样式与交互 100% 可控、依赖少;两端点场景数据量小,自绘完全足够。

## ADR-001 · 技术栈:Tauri 2 + React + tshark 引擎

- **状态**:✅ 已定(2026-08-07,用户确认)
- **背景**:跨平台桌面工具,需安装包、小体积、开箱即用;解析需覆盖大量协议。
- **决策**:
  1. 桌面外壳 **Tauri 2**(vs Electron:安装包 ~10MB vs ~100MB+,内存低)。
  2. 解析引擎 **tshark 打包内置**(vs 自研解析:约 3000 协议覆盖 vs 几十种;pcapng/gzip 原生支持)。
  3. 前端 **React + TS + Vite**,后端 Rust 薄封装(调 tshark 子进程 + 读输出)。
- **后果**:
  - 依赖:分发需附 tshark 二进制(~15MB)与 GPL 许可证文本。
  - 隔离:tshark 以子进程调用,不修改/不链接其代码,仅整合分发,规避深层传染;随包附许可证文本(与 Wireshark/tshark 的 GPL-2.0 兼容做法)。
  - 前端做解析与聚合(文件规模小),后端保持薄。

## ADR-000 · 文档组织按类别分目录
