# pUI 报文分析能力升级计划

> 状态：待审批  
> 日期：2026-08-25  
> 设计依据：`docs/pUI_报文分析能力升级指南.md` 第 1-16 项  
> 产品目标：把 PCAP 中分散的报文还原为可验证的网络故障事件和证据链。

## 1. 审批摘要

当前 pUI 已经具备稳定的 PCAP 打开、字段解析、双向会话聚合、异常标签统计、时序图、报文详情和 PNG/Markdown 导出能力，适合作为升级基础；但分析结论仍以 tshark 标签和会话级提示为主，尚未形成 TCP 字节流状态、事件关联和证据模型。

本计划建议按以下依赖顺序升级：

```text
字段与流身份契约
  -> 结构化 Evidence 模型
  -> TCP Seq/ACK/SACK/RTT 状态跟踪
  -> Gap 与事件状态机
  -> Top Events / Why / Incident Timeline
  -> Sequence Space / Health Score
  -> 报告与业务体验关联
```

审批后首先执行 M0，不直接开发 Health Score 或复杂可视化。原因是这些上层能力必须消费同一套、可测试的事件证据，不能继续从标签数量反推结论。

## 3. 当前架构结论

当前主数据流为：

```text
open_capture
  -> Rust 调用 tshark -T json -e <精选字段>
  -> parsePackets: JSON -> Packet[]
  -> aggregateConversations: Packet[] -> Conversation[]
  -> analyzeConversationIssues: tshark 标签/简单规则 -> ConversationIssue[]
  -> Zustand AppState
  -> 会话/主机/摘要/拓扑/时序图/报文详情
  -> PNG 或逐包 Markdown 导出
```

可复用基础：

- tshark 子进程已有超时、输出上限、stderr 排空、路径校验和异步隔离。
- 前端已有解析上限、加载竞态保护、Hex LRU/并发去重、长会话抽稀和错误边界。
- `parse`、`aggregate`、`filter`、`stats` 多为纯函数，适合继续按 TDD 扩展。
- 时序图、摘要统计、搜索高亮和点击跳包可以复用为事件下钻入口。

核心断层：

- `Packet` 只有 Seq、ACK 和 5 类 tshark 标签，缺少 TCP stream id、payload length、SACK、窗口和 RTT 等事实。
- 会话 key 只按端点归并；同一端点对复用端口或并发连接时，不足以作为 TCP 状态机身份。
- `Packet.len` 是帧长度，不能用于计算 TCP 序列号推进。
- `ConversationIssue` 只有类型、文案和单个报文号，无法表达证据、推断、限制和恢复过程。
- 当前 Markdown 是逐包叙述，不是分析报告；没有 JSON/HTML 报告契约。

## 5. 目标架构与数据契约

新增分析层，不让 UI 直接依赖 tshark 显示字符串：

```text
Capture JSON
  -> PacketFacts / CaptureQuality
  -> Stream Builder (tcp.stream 优先，端点 key 降级)
  -> TCP State Engine
       - Sequence Tracker
       - ACK Tracker
       - SACK Tracker
       - RTT / Window Metrics
       - Gap Detector
  -> Event Engine
  -> StreamAnalysis / Evidence JSON
       - observations
       - inferences
       - limitations
       - metrics / gaps / events / application impacts
  -> UI / Markdown / JSON / HTML
```

建议新增的核心模型：

- `CaptureAnalysis`：schemaVersion、captureQuality、streams、全局摘要。
- `TcpStreamAnalysis`：stream id、端点、指标、gaps、events、score、限制。
- `Observation`：可直接从报文验证的事实，必须引用 packet number 和字段值。
- `Inference`：规则推断、置信等级、所依赖的 evidence id，不允许孤立结论。
- `Limitation`：单观察点、缺握手、截断、采集统计不可用等限制。
- `SequenceGap`：方向、起止序列、字节数、首次观察、SACK、填补报文、存续时间。
- `TcpEvent`：类型、状态、时间范围、严重度、证据列表、相关报文、恢复状态。
- `ApplicationImpact`：协议、阶段、时间窗口、相关 TCP event、保守措辞。

模型要求：

- 带 `schemaVersion`，JSON 可供 UI、报告、未来 CLI/API 复用。
- 分析结果可序列化且确定性输出；相同输入产生相同 event id 和排序。
- 任何 inference 至少引用一条 observation；任何确定性不足都进入 limitation。
- Sequence 运算使用 TCP 32 位序列号比较，覆盖回绕、SYN/FIN 消耗和重叠段。

## 6. 分阶段实施计划

### M0：事实契约与测试样本

目标：先让分析引擎拿到正确事实，并冻结输出语义。

- 扩展三处同步的 tshark 字段契约：Rust `CAPTURE_FIELDS`、TS `captureFields.ts`、fixture 生成脚本。
- 至少增加 `tcp.stream`、`tcp.len`、窗口、SACK block、ACK RTT、spurious/zero-window/window-full 等必要字段；实际名称先用 `tshark -G fields` 针对支持版本验证。
- 增加 `frame.cap_len` 等可用的捕获完整性事实；取不到采集 drop 统计时明确记为 unknown。
- 新建分析 schema 和 `src/analysis/` 目录，不改 UI 行为。
- 增加真实/合成 PCAP：连续传输、单 Gap+SACK+恢复、乱序后补齐、spurious retransmission、Zero Window、RST、mid-stream、SnapLen 截断。
- 建立前后端字段清单一致性测试和 fixture golden test。

验收：字段在平铺/树形 tshark JSON 下都能解析；现有 188+17 测试不回归；每个新增事实至少有一个失败测试先行并转绿。

### M1：会话身份、健康指标与捕获限制

目标：形成可信的 Stream 基线，不再把 tshark 标签直接写成故障结论。

- Stream Builder 优先使用 `tcp.stream`；无该字段时才使用现有端点 key，并记录降级 limitation。
- 输出包数、字节、时长、重传、快速重传、Dup ACK、SACK、OOO、lost segment、Zero Window、Window Full、RST、SYN/SYN-ACK 重传、RTT 分位数和 variation。
- 建立 `CapturePerspective = single-observation-point | multi-point | unknown`；默认不自动声称网络节点位置。
- 建立 Capture Quality：截断帧、缺握手/mid-stream、多接口、采集统计是否可用；未知值不得显示成 0。
- 改造旧 `ConversationIssue` 文案，使观察、推断和限制分开；保留旧筛选兼容映射。

验收：统计由结构化事实得出；中途抓包不会生成确定性“丢包”结论；RTT/窗口/连接指标有 golden tests。

### M2：TCP Sequence Gap Engine

目标：逐方向还原 TCP 字节序列空间及 Gap 生命周期。

- 实现 32 位序列号工具和 interval/range 合并。
- 实现双向 Sequence Tracker、ACK Tracker、SACK Tracker。
- 检测 Gap 起止、大小、首次/最后观察时间、后续 SACK、是否填补、填补报文、存续时间。
- 区分：重复段、重叠重传、乱序补齐、未恢复 Gap；SYN/FIN 正确消耗一个序列号。
- 保持每个 stream O(n log k) 或更优，避免复制全量 Packet。

验收：指南中的 ACK/SACK 示例能产生确定 Gap；回绕、重叠、缺字段、mid-stream 均有单测；10 万包分析满足性能基线且 UI 不崩溃。

### M3：TCP Event Engine、Why 与 Incident Timeline

目标：把分散报文组织成可点击、可解释的故障事件。

- 实现事件状态机：Possible Loss/Delayed Segment、Reordering、Possible ACK Loss/Spurious Retransmission、Zero/Full Window、Reset、Connection Setup。
- 事件串联 Original Segment、ACK 停滞、Dup ACK/SACK、Retransmission、Recovery ACK。
- 生成稳定 event id、开始/结束、状态、严重度、证据完整度、相关 packet numbers。
- Top Events 先按严重度、未恢复状态、持续时间、证据完整度排序；不使用 Health Score 代替排序。
- 在现有报文详情旁增加 Why；增加事件级 Timeline，点击节点复用 `selectPacket` 和 highlight。

验收：三个 canonical 场景能稳定分类；无 meaningful gap 的重传不得归为确定性数据丢失；任意事件可从 UI 跳到所有关键报文。

### M4：Sequence Space、Health Score 与诊断工作区

目标：让用户先看到会话健康和高价值事件，再进入报文细节。

- 将右侧升级为诊断视角：Overview、Incidents、Sequence Space、Packets；保留现有时序图。
- Overview 显示健康指标、Observed/Inference/Limitation 和 Top Events。
- Sequence Space 展示双向序列轴、Gap、SACK block、填补位置和 hover 证据。
- Health Score 使用版本化、透明公式；采用比例/持续时间/严重事件而非纯数量，并展示扣分明细。
- Score 仅用于筛选/排序，不作为诊断结论；证据覆盖不足时显示 unavailable，而不是给满分。

验收：事件和 Sequence Space 共用同一分析模型；点击/hover 不改变布局尺寸；键盘可达和 reduced-motion 行为通过组件测试。

### M5：证据化报告

目标：同一 `CaptureAnalysis` 生成机器可读和人可读报告。

- 保留现有“逐包时序叙述”，新增“TCP 分析报告”。
- JSON：完整、版本化 Evidence schema。
- Markdown：Summary、Observed、Inference、Limitation、Top Events、事件证据链、业务影响。
- HTML：单文件离线报告，所有抓包来源文本必须转义，不加载远程资源。
- PDF 后置；先评估系统打印或 HTML-to-PDF 的跨平台一致性再立项。

验收：三种格式语义一致；snapshot 可重复；恶意 URI/info/DNS 内容不能注入 Markdown/HTML；报告事件可定位原 packet number。

### M6：业务体验分析与关联

目标：在 TCP 引擎稳定后增加应用层体验，不把时间相关误写成因果。

- 建立插件式 `ApplicationAnalyzer` 接口。
- 第一批复用现有事实完成 HTTP、DNS、TLS/HTTPS；只分析握手、响应和时延，不声称解密内容。
- 第二批按字段可用性加入 SSH、RDP、VNC、SMB；每个协议单独审批字段和规则。
- 用时间窗口、阶段重叠和事件严重度生成 `ApplicationImpact`，措辞限定为“时间和行为相关，可能影响”。
- 无应用层阶段证据时只输出 TCP 结论，不猜业务状态。

验收：有/无 TCP 相关事件的对照 fixture 不误报；TLS 不读取明文假设；每条影响结论引用应用事实和 TCP event。

## 7. TDD 与质量门槛

每个任务遵循 Red -> Green -> Refactor，并在验证后单独提交。测试层次：

| 层次 | 必测内容 |
|---|---|
| Parser contract | tshark 版本差异、数组/树形/平铺 SACK、缺字段、异常字段 |
| TCP primitives | 回绕、SYN/FIN、重叠、乱序、重复段、ACK/SACK range |
| Event engine | Loss/Delay、Reorder、ACK Loss、Window、RST、恢复/未恢复 |
| Capture limitations | mid-stream、snaplen、多接口、统计未知，限制不得升级成结论 |
| Application | 有相关/无相关对照、加密协议边界 |
| UI | Top Events、Why、Timeline 跳包、Sequence Space、空/错/大数据状态 |
| Report | JSON schema、Markdown/HTML snapshot、安全转义、确定性排序 |
| Integration | 真实 tshark fixture 从 PCAP 到 Evidence Report |
| Performance | 1 万/10 万包基线；事件数量和证据数组设内存护栏 |

每个里程碑统一执行：

```text
npm test
npm run build
cargo test --manifest-path src-tauri/Cargo.toml
git diff --check
```

涉及真实桌面交互的阶段还需运行 Tauri 冒烟：打开 PCAP、选择 stream、事件跳包、导出报告。

## 8. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| tshark 字段随版本变化 | 启动时记录版本；字段能力探测；fixture 覆盖支持区间；缺字段降级为 limitation |
| 同端点多连接被合并 | M1 前置 `tcp.stream` 身份；禁止在旧 flow key 上运行状态机而不标记降级 |
| TCP 序列算法误判 | 32 位 serial arithmetic；canonical PCAP；双向状态独立；规则版本化 |
| 单端/漏抓导致过度结论 | 强制 Observed/Inference/Limitation；默认单观察点/未知；不定位具体节点 |
| 128MB JSON 内存放大 | 分析 O(n)；避免深拷贝；设置 event/evidence 护栏；M2 做 10 万包性能门禁 |
| UI 被长会话拖慢 | 事件折叠、虚拟化/抽稀、按需渲染 Sequence Space，不削减分析输入 |
| 报告注入 | 所有抓包文本按输出格式转义；HTML 禁止远程脚本/资源 |
| Score 被误当结论 | 显示公式版本和扣分项；覆盖不足时 unavailable；报告中注明仅供筛选 |

## 9. 审批边界

本次建议审批以下内容：

1. 同意 Evidence-first 目标架构和 1-16 项覆盖范围。
2. 同意按 M0 -> M6 的依赖顺序执行，不按指南展示顺序直接堆 UI。
3. 同意首轮只批准 M0-M3，完成 Event Engine 后进行一次规则准确性复审，再批准 M4-M6。
4. 同意 PDF 和第二批应用协议不进入首轮承诺。

本计划不包含 AI 自动判断。未来若引入 AI，只允许消费版本化 Evidence JSON，用于解释、摘要和排查建议，不替代 TCP 状态机。

## 10. 建议审批结论

建议：**有条件批准 M0-M3**。

开始实现前需要确认两个产品口径：

- pUI 对所有普通 PCAP 默认展示“单观察点/无法定位具体丢包节点”的限制，除非后续存在明确多点抓包元数据。
- Health Score 只用于排序和筛选，不能进入“确定故障结论”字段。

批准后，第一个开发提交应是 M0 的失败测试、字段契约和 golden fixtures，不应先提交 UI 原型。
