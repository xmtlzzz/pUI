# M4 案例 3:Possible ACK Loss / Spurious Retransmission —— 重传不等于数据丢失

> 数据来源(冻结,唯一事实):`docs/specs/m4-cases/data/case-3-spurious.json`(同一目录 `.pcapng` 为同一抓包)。
> 对照基线形状:`reference-normal.json`(仅取其"握手 -> 逐段 ACK 即时推进"的形态,见第 4 节保真声明)。
> 本文所有报文号、seq/ack/len、字节数均引自上述 JSON;右侧正常参考一律使用示意编号,禁止使用真实 packet number。

## 0. 案例事实摘要(全部来自冻结 JSON)

| 项 | 值 |
|---|---|
| 抓包规模 | 9 个报文(#1–#9),时间 0 – 0.31s,方向 c2s / s2c |
| 握手 | #1 SYN(seq=0) / #2 SYN+ACK(ack=1) / #3 ACK —— 完整,`facts.midStream=false` |
| 上行数据 | #4(seq=1,len=100) → #6(seq=101,len=100) → **#8(seq=101,len=100,重发)** |
| 下行确认 | #5 ack=101 → #7 ack=201 → **#9 ack=201(未前进,`duplicate-ack`,dupNum=1)** |
| 序列空间 | `facts.gaps=[]`(零缺口);`seenBytes.c2s=201`,`seenBytes.s2c=1`;`unorderableInput=false`;`lengthUnavailable=false` |
| #8 分类 | `pure-duplicate`(newBytes=0/100);tshark 标注 `retransmission, spurious-retransmission` |
| 事件(1 个) | id `0:c2s:possible-ack-loss-or-spurious:101`;kind=`possible-ack-loss-or-spurious`;direction=c2s;0.30s→0.31s;severity=**low**;recovered=**true**;evidenceScore=3;`duplicateAckPackets=[]`;`sackPresent=false` |

M3 验收线在本案例的体现:**`gaps=[]` + `pure-duplicate` 的重传,引擎判定为 `possible-ack-loss-or-spurious`(low),推断措辞为"更可能是确认未被发送端及时看到(ACK 丢失/延迟),而非数据丢失"** —— 无 meaningful gap 的重传不得判为数据丢失。

## 1. 静态布局(桌面 `1fr 1fr`)

本案例是对布局系统的压力测试:左侧没有任何 Gap 图形可画,"Gap/SACK/恢复图形化"槽位改由**零缺口序列空间全绿视图 + 重发叠加层**承担。

要点:左侧事件卡固定呈现"严重度 low / 已恢复 / DupACK×0 / SACK 无",与 case-1(Gap+SACK 风暴)形成视觉反差——**这里什么都没有缺**;Why 面板三层严格按引擎输出顺序排列(observations → inference → limitations),限制两条原文展示。

零缺口布局压力测试说明:case-1/case-2 的左栏图形槽位是"缺口红块 + SACK 块 + 回补动画";本案例该槽位必须退化为"全绿实心条 + 重发虚线叠加层"。设计约束:叠加层只做视觉标注,不得让 101–200 区间呈现任何"未覆盖/待回补"状态(它已被 #6 覆盖且被 #7 确认),也不得复用 case-1 的红色缺口配色——配色语义在三个案例间保持一致:绿=已观察,红=缺口,虚线=重复段。

## 7. 措辞合规自检

- 观察与推断分离:E1 三条 observation 各自带 `packetNumber` + 字段值(#8 / `tcp.seq_raw=101` 等),inference 声明 confidence=`medium` 且 `evidenceRefs` 完整指向 o1–o3,无孤立结论。
- 不断言确定性丢包:全文不出现"确认丢包/丢数据";重传统一表述为"重发/伪重传",根因表述为"更可能是……而非……"(与引擎 inference 原文一致)。
- 单观察点限制必须出现:§1 [限制] 对应引擎 limitations 全部两条(ASCII 图内因版面为节选;实现须展示完整原文,含「可确认本地观察到的到达情况」与「(网卡/ring buffer/镜像口),缺口不等于网络丢包」),在默认态即可见,不因播放/降级隐藏。
- tshark 标签只作观察(o3 引用 `retransmission, spurious-retransmission` 标注),不作结论依据——结论由 o1/o2 的序列空间事实支撑。

## 审批记录(2026-08-26)

**结论:批准,附一条强化要求**(三案统一,全文见 case-1 审批记录)。

> 要求:报文交互过程必须有**明显的阶段标注**——时间线上把交互划分为命名清晰的故障阶段,
> 每个阶段的起止报文、持续时长、该阶段发生了什么都要在图形上直接可见。

本案例的阶段划分(由引擎事件链导出):

`① 正常发确(#1–#7)` → `② 静默窗(0.06s–0.30s,无新数据)` →
`③ 冗余重传(#8,pure-duplicate)` → `④ 确认无变化·已恢复(#9,ACK 停在 201)`

阶段带/当前阶段高亮/阶段信息面板的实现约束与验收方式同 case-1 审批记录第 4 条:
阶段边界从引擎输出确定性推导,视图模型层新增 stage 推导纯函数并有单测。
注意本案例 §2 分镜 S4「静默」升级为显式命名阶段——静默本身是证据
(240ms 内发送端未收到确认才重传),必须在阶段带上可见。
